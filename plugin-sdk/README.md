# iHub Plugin SDK

`@ihub/plugin-sdk` is the small TypeScript boundary between a plugin frontend and the iHub desktop host. It has no React, Node.js, or Tauri package dependency; a plugin can therefore ship a compact Vite bundle and still receive typed commands, search requests, a host-owned sub-input, settings, clipboard, a separately permissioned read-only clipboard-history snapshot, shell, narrowly scoped user-selected filesystem APIs, native-worker calls, a bounded focus lease for a browser screen picker, fixed layout actions for iHub's own launcher, and an explicitly attached launcher-context transfer. `process.spawn` is not an SDK host API; a plugin that needs local execution uses its manifest-locked native worker.

For filesystem work, a frontend must first call `ihub.filesystem.selectDirectory()` or `ihub.filesystem.selectFiles()`. Native pickers return short-lived opaque `grantId` values, not reusable path permissions. `selectFiles()` exposes only names and sizes to browser code; a plugin with `nativeApi: true` can consume that one-shot grant through `ihub.native.runCommand()`, and only its declared worker receives canonical paths. The current write-capable API is intentionally narrow: `previewBatchRename()` creates a host-owned preview token, and `applyBatchRename()` accepts only that same grant plus token. A plugin never submits an arbitrary rename list for execution.

For a uTools-style “send this selection to a plugin” action, declare only the needed `permissions.launcherContext` flags: `text`, `files`, and/or `image`. iHub never sends these automatically. Its trusted parent must first receive a real user selection, stage a short-lived context for one declared **frontend** command, then dispatch that command with the opaque `contextId`. The command event exposes only `invocation.launcherContext`; call `await ihub.launcherContext.consume(invocation.launcherContext.contextId)` inside that handler to take the payload once. Text is bounded; files contain canonical name/kind/size metadata and opaque handles but no paths or file access; image data is an opaque PNG handle and metadata but no pixels. This API neither reads the live clipboard nor upgrades a frontend or native worker's filesystem capability.

For browser `getDisplayMedia` flows, declare `"screenCapture": true`. The trusted host adds `allow="display-capture"` to the cross-origin iframe only when the native-issued lease is still active and validated as a visible `Surface` for a manifest that declares that permission; hidden search runtimes, undeclared plugins, expired leases, and browser safety previews receive no delegation. Start `ihub.screenCapture.acquireFocusLease()` immediately before the user-driven picker, but **do not await it before** calling `getDisplayMedia()`—the async iframe/host round-trip can consume Chromium's transient click activation. Call `getDisplayMedia()` synchronously, then await/release the opaque lease in `finally` while safely handling a failed acquisition. Delegation and the focus lease do not grant screen pixels, bypass the browser/OS picker or OS permission, or expose a native capture API. The lease only protects the iHub surface from temporary focus loss; it is limited to one per plugin, four globally, and a 90-second host deadline. Browser-only QA cannot prove desktop capture permission or successful frame delivery.

For browser microphone capture, declare `"microphone": true` independently. The trusted host adds `allow="microphone"` only to a native-validated visible `Surface` lease whose manifest declares that exact boolean permission. Hidden search runtimes, undeclared plugins, expired leases, and browser safety previews receive no delegation. This does not bypass Chromium or operating-system consent, expose a native audio API, or imply `"screenCapture"`; request audio with the browser's user-driven media APIs and handle denial normally.

For one system color under the mouse, declare `"cursorColor": true` and call `await ihub.cursorColor.sampleOnce()` only from an explicit visible-page action. iHub shows its own confirmation before sampling, then waits two seconds and returns only `{ hex, rgb }`. The SDK keeps this one request open for up to two minutes so an initial macOS Screen Recording permission prompt can finish; it never turns the capability into a background task. It never exposes cursor coordinates, screenshots, display/window identity, recording, or a background polling API; hidden search runtimes are rejected.

Declare `"windowManagement": true` before calling `ihub.windowManagement.manageLauncher()`. The host accepts only `center`, `snap-left`, `snap-right`, and `toggle-always-on-top`, and applies them only to iHub's `main` launcher window. This permission never enumerates, focuses, reads, or controls other applications' windows and never accepts caller-supplied coordinates.

```ts
import { bootstrapPlugin } from "@ihub/plugin-sdk";

await bootstrapPlugin("ihub-plugin-example", async (ihub) => {
  await ihub.subInput.set(({ text }) => {
    ihub.logger.debug("Sub-input changed", { text });
  }, "Search", true);

  await ihub.commands.register(
    { id: "hello", title: "Say hello" },
    () => ({ message: "Hello from iHub", close: true }),
  );
});
```

`ihub.subInput.set`, `setValue`, and `remove` control only the trusted input in the current visible plugin surface. The iframe keeps the change callback locally; the host receives bounded strings only. Hidden search runtimes cannot create or mutate the input, and replacing, closing, disabling, or disposing the surface clears both its value and callback.

During `bootstrapPlugin`, the SDK also installs the same frozen object as `window.utools` and `window.rubick` for a deliberately small migration path. It includes the three familiar sub-input names plus existing permission-checked `copyText`, notification, external/path open, and confirmed one-pixel color APIs, along with read-only theme/platform helpers. It does **not** emulate the Electron preload surface: there is no `require`, `fs`, `child_process`, `remote`, `BrowserWindow`, arbitrary preload/shell, database, raw path picker, input simulation, or screen/window enumeration. Existing globals are never overwritten and are restored on runtime disposal. This is bootstrap-time source compatibility for SDK-based plugins, not a promise that an unmodified uTools package can be dropped into iHub.

Use `manifest.schema.json` in editor validation and read [`../docs/PLUGIN_DEVELOPMENT.md`](../docs/PLUGIN_DEVELOPMENT.md) for the package, binary-backend, permission, and GitHub import contracts.

Manifest `icon` (or its `logo` alias) and static `contributes.commands[].icon` entries are package-relative PNG, JPEG, or WebP files. Artwork paths cannot contain traversal/dot or empty components, control characters, colons, trailing dots/spaces, or Windows device names; a manifest may declare at most 64 commands and reference at most 32 distinct artwork candidates. The native host rejects a package with an invalid top-level identity image, while an unavailable or unusable command icon from a legacy package safely falls back to the host icon instead of rejecting the whole plugin. Accepted artwork is bounded, decoded, and re-encoded to a PNG data URL; plugin filesystem paths and original bytes never enter the WebView. Dynamic `ihub.commands.register()` definitions do not accept artwork and defensively strip an `icon` property supplied by untyped JavaScript.

Global shortcuts are also static manifest declarations. Set `permissions.globalShortcut: true`, then use `contributes.commands[].shortcut` for a direct command binding or `contributes.globalShortcuts[]` for an explicit `commandId`/`keyword` target. Rust canonicalizes the portable accelerator, reserves the launcher and Alt+F4 bindings, rejects duplicate/over-limit mappings, and reports native registration failures in Plugin Center without disturbing the main launcher shortcut. A keyword mapping opens iHub with that bounded query; it never silently executes a fuzzy result. Runtime `commands.register()` cannot introduce a shortcut, and the SDK defensively strips an untyped `shortcut` property just as it strips dynamic artwork.

`ihub.developer.createProject()` creates a new template only after the user has granted a directory scope. It returns the canonical project path and manual next steps; it never installs dependencies, starts Vite, or runs generated/native code. The generated `pnpm build` command finishes with a read-only pre-link check for `plugin.json`, `dist/`, and any explicitly declared binary paths. Developers still choose when to build and explicitly link the local project in iHub.

The SDK is an ergonomic IPC client, not a sandbox. A plugin with a native binary can execute with the installing user's privileges; iHub surfaces declared capabilities and package provenance, but users must install only code they trust.
